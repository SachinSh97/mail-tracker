# Deploy Seenly to Render

Both parts run on Render, created together from [`render.yaml`](render.yaml):

| Render service | What                          | Address (default)                 |
| -------------- | ----------------------------- | --------------------------------- |
| `seenly-app`   | Web app (static site)         | `https://seenly-app.onrender.com` |
| `seenly-api`   | Service: API + tracking pixel | `https://seenly-api.onrender.com` |

The web app forwards everything under `/api` to the service. The browser only ever talks to the web app's
address, so the session cookie works as a normal same-site cookie. Tracking pixels in emails point straight at
the service.

> **Choose the service's address before sending real tracked emails.** Every pixel has it baked in; if it changes
> later, emails already sent stop reporting opens.

Takes about 30 minutes. You need a GitHub account, a [Neon](https://neon.tech) account, and access to the Google
Cloud project used for sign-in.

---

## 1. Push the code to GitHub

Create a repository (private is fine) and push this project to it, `main` branch.

## 2. Create the production database (Neon)

1. In Neon, create a project (or a new branch/database for production).
2. **Connect** → copy the **pooled** connection string (its host contains `-pooler`). Keep it for step 3.

## 3. Create both services on Render

1. Render dashboard → **New** → **Blueprint** → connect GitHub → pick the repository.
2. Render reads `render.yaml` and lists `seenly-api` and `seenly-app`. Fill in the values it asks for:

   | Service      | Variable                | Value                                                        |
   | ------------ | ----------------------- | ------------------------------------------------------------ |
   | `seenly-api` | `DATABASE_URL`          | the pooled Neon connection string from step 2                |
   | `seenly-api` | `GOOGLE_CLIENT_ID`      | your Google OAuth client ID (`….apps.googleusercontent.com`) |
   | `seenly-api` | `PUBLIC_BASE_URL`       | `https://seenly-api.onrender.com`                            |
   | `seenly-api` | `CORS_ORIGINS`          | `https://seenly-app.onrender.com`                            |
   | `seenly-app` | `VITE_GOOGLE_CLIENT_ID` | the same Google client ID                                    |
   | `seenly-app` | `VITE_SITE_URL`         | `https://seenly-app.onrender.com`                            |

| `seenly-app` | `VITE_CONTACT_EMAIL` | an email address shown on the privacy page (public) |

`SESSION_SECRET` is generated by Render. `NODE_ENV`, `NODE_VERSION`, `TRUST_PROXY_HOPS` and `VITE_API_URL` are
already set in the file.

3. **Apply**. The first build of the service also creates the database tables (`npm run db:deploy` runs during
   every build, so later database changes are applied automatically).

**If Render gave a service a different address** (e.g. `seenly-api-x7k2.onrender.com` because the name was taken):
put the real addresses in the four "address" variables above, and change the `/api/*` destination in
`render.yaml` to the real service address, then push.

## 4. Allow the address in Google sign-in

Google Cloud Console → Google Auth Platform → **Clients** → your Web client:

- **Authorised JavaScript origins:** add `https://seenly-app.onrender.com`
- **Authorised redirect URIs:** add `https://seenly-app.onrender.com/auth/callback`

While the consent screen is in **Testing**, only the test users listed there can sign in. To let anyone sign in,
open **Branding** and fill in:

- **App name:** Seenly · **User support email:** yours
- **App home page:** `https://seenly-app.onrender.com`
- **App privacy policy link:** `https://seenly-app.onrender.com/privacy`
- **Authorised domains:** `seenly-app.onrender.com`

then **Audience → Publish app**. Seenly only asks for `openid email profile`, so Google shouldn't require a full
verification review.

## 5. Check it works

1. Open `https://seenly-api.onrender.com/health` → `{"status":"ok", … "database":"up"}`.
2. Open `https://seenly-app.onrender.com`, **Sign in with Google**.
3. Create a tracker, copy the pixel, paste it at the end of a Gmail draft, send it to **another** account.
4. Wait a minute (opens within 60 s of creating the tracker are ignored), then open the email in the other account.
   The email should show **Opened**, the bell should count it, and an open email screen should update by itself.

### Check the real IP reaches the service

The service compares the IP that created a tracker with the IP that opens it, to ignore your own opens. Both must
be real visitor IPs, not Render's.

1. Look up your public IP (e.g. search "what is my ip").
2. Create a tracker in the app, then in Neon's SQL editor run:
   `select creator_ip from trackers order by created_at desc limit 1;`
3. - It's **your IP** → nothing to do.
   - It's **another address** → requests reach the service through more proxies (the `/api` forwarding adds one).
     Set `TRUST_PROXY_HOPS` to `2` on `seenly-api`, redeploy, and check again.

### Check live updates

With an email's screen open, open that email in the other account. If the screen doesn't update by itself within a
few seconds, Render's `/api` forwarding is buffering the live-updates stream. Everything else still works; screens
then update when you revisit them or return to the tab.

## Free plan: missed opens

The free service sleeps after ~15 minutes without traffic and takes 30+ seconds to wake up. Gmail fetches the pixel
when an email is opened and gives up before then, so **opens of a sleeping service are lost**.

- **Starter plan** for `seenly-api` (paid): never sleeps. Change `plan: free` to `plan: starter` in `render.yaml`.
- **Stay free**: point a free uptime monitor (e.g. UptimeRobot) at `https://seenly-api.onrender.com/health` every
  5 minutes. Check Render's current free-tier hour limits, since this keeps the service awake all month.

## Later changes

Every push to `main` redeploys only the part that changed (`client/` or `service/`). Database migrations run as part
of the service's build.
